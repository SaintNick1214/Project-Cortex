# Time-only expiry delivery assessment

This is a read-only implementation assessment for original03-final/16, following [the Task12 follow-up](../task12-asset-functional-v2-20261008/03-final-query-expiry-followup.md). It is not an acceptance verdict. Repository root: `/Users/SaintNick/Documents/Cortex/worktrees/backend-runtime-completion`. No product edits, build, deployment, service mutation or inference occurred. The frozen Task12 candidate remains unchanged.

The remaining concrete problem is a payload query whose authorization depends on wall-clock expiry while the browser retains its previous result. Adding another cached authorization query does not make delivery fresh. The existing authority checks are correct when executed; execution is the missing boundary.

## Evidence and limits

- Installed Convex1.46 `node_modules/convex/src/browser/simple_client.ts:540` returns `localQueryResult` immediately in `query()`. Its `onUpdate()` at line191 schedules an initial callback from an already available result, without waiting for a new server result. A local, network-free call to the actual `ConvexClient.prototype.query` returned the controlled cached object after a controlled deadline, with zero new subscription requests. This proves the installed cache fast path, **not a new native grant-expiry exploit**.
- Current `src/client-runtime/client.ts:75` obtains session authority through a query; `inSession()` repeats that query before/after I/O, and `watch()` at line136 repeats it before delivering cached result callbacks. A still-valid JWT and unchanged principal/scope do not detect an expired runtime grant this way. Reconnect uses these same paths.
- `convex-dev/runtimeAuth.ts:122` checks `grant.expiresAt`; provisioning at line294 persists it without scheduling an expiry mutation. `runtimeDataAuth.ts:166` also checks conversation retention and share expiry. These clocks passing do not change their database documents. [Convex's official best practices](https://docs.convex.dev/understanding/best-practices#dont-use-datenow-in-queries) explicitly say subscribed queries do not rerun merely as time passes; server cache reuse may be shortened for time-dependent queries. Therefore **unbounded server HTTP query caching is not established**.
- The prior native [Task11 diagnosis](../task11-graph-functional-v2-20261008/native-actual/native-expiry-query-diagnosis1.json) actually denied both expired query and mutation and records `queryClockCacheHypothesis:false`. It must not be cited as an exploit. Task12's [native lifecycle result](../task12-asset-functional-v2-20261008/native-actual/native-lifecycle1-outcomes.json) proves the repaired fresh artifact mutation denies the same arguments after an eight-second grant expiry, with the artifact unchanged.
- Principals and memberships currently have version/revoked/deleted fields, **no time-only expiry field** (`runtimeAuthSchema.ts:36–46`). Their revoke/delete operations change database dependencies. JWT expiry and official authentication refresh are separate from runtime-grant expiry. No new failure of either is claimed here.

## Minimal repair and ownership

1. Convert supported sensitive public payload reads to fresh mutations while reusing their existing bounded handler logic, ownership/source/share checks and DTOs. Remove the corresponding public payload-query registrations; an SDK-only session check would leave direct public query callers exposed. Start with session, observe and run/history reads, then the remaining functional data/metadata families above. Update exact SDK reference kinds and generated APIs through ordinary codegen. Preserve control-only cancellation after definition revocation and all paid accounting behavior.
2. Preserve reactivity with a small authorized **change-signal query**, carrying only a requested resource's opaque revision/cursor marker, never text, approvals, asset refs, cached context or policy details. On notification, fetch the fresh payload mutation. Coalesce notifications to one in-flight fetch per resource/page, preserve attempt+sequence cursors and final-only behavior, and deliver callbacks only after the current auth generation/principal/scope is checked. Existing durable output throttling avoids a mutation per raw model token.
3. Return a server-derived delivery deadline bounded by the actual grant and any relied-on share/retention/witness deadline. Client timers clear retained displays and Blob previews at that deadline, and reconnect/visibility/resume require fresh delivery. Timers do not grant permission; the fresh server mutation remains authoritative. Generation-fenced scheduled expiry writes may invalidate subscriptions sooner, but delayed scheduler execution cannot be the sole exact expiry guard. No caller-supplied clock or cache-busting nonce establishes authority.

Recommended later execution split: **Root** owns the shared fresh authority/deadline + safe signal contract and browser watcher/remote transport integration (`runtimeAuth.ts`, `runtimeAuthSchema.ts` only if needed, `runtimeClient.ts`, `src/client-runtime/{client,types,validation}.ts`, provider remote adapter). **This author** owns payload registration/helper composition and corresponding legacy SDK adapters across the exact backend families above (`runtimeDataAuth.ts`, `runtimeMetadataAuth.ts`, `runtimeRegistryAuth.ts` only as concretely required); internal action-delivery references follow the final audit. **Native executor** proves same-JWT short-grant/share expiry on a connected browser, reconnect/cached prefix, ordinary authorized streaming and fresh HTTP/action returns, without inference merely to test expiry. **Existing reviewer** reviews the one coherent repair and final03/16 outcomes; this document introduces no extra gate.

Decisive future regressions: unchanged-data grant expiry; selective evidence-share expiry while a separate view permission remains; reconnect after expiry with retained text; ordinary authorized stream/cursor replacement; expired observer suppression and UI clearing; renewal of the same principal without losing permitted access; DB-based principal/membership revoke negatives. Each claims only the delivery/effect class actually exercised.
