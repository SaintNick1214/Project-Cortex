**Outcome: exact native rejection cause remains unknown; an external Convex auth-notification limitation explains the client timeout. No demonstrated lost-rejection bug in Cortex. The original expired-token exact-code gate remains FAIL.**

This bounded, read-only investigation used source `acf3b5efa4d1d3b798fa655b0db919cf6baf7f40`, the retained actual K11 receipt SHA `64e3ec9fb90e0b5829db0ec9c98d1a3a54e92774fd8a1ca800f4556a0582d300`, and installed Convex **1.46.0**. All four retained official source pins match the local installed source. Cortex runtime client source SHA `14a255e57bd8cbbd9a57adc9f37ab2c49e8a76e61e18ca2f2779d39e31ef163c`. No service calls, source edits, paid calls or test reruns were performed.

The expired signed token produced two socket-open/close/reconnect cycles, no observed AuthError, no force-refresh fetch and no official auth boolean callback. Cortex rejected at **4002.110709ms** with configured **4000ms** and `AUTHENTICATION_TIMEOUT`, zero protected payloads and zero runtime RPCs. The invalid-signature control received a native AuthError, requested force refresh once, received the unchanged case token, reported official false, and reached Cortex `UNAUTHENTICATED` at **1568.996125ms**. Its official false callback reached the SDK; the adapter did not discard it. Valid owner metadata passed. These are actual observations, not native verifier-cause proof.

The observed expired-token sequence is therefore sufficient to explain **why this client remained pending until its timer**: the official manager was awaiting cached-token confirmation while the transport reconnected, and Cortex received no terminal auth callback. It does **not** establish why the server closed the connection. The diagnostic intentionally discarded close codes/reasons, raw protocol error fields and non-whitelisted log arguments; those missing details cannot be reconstructed from counters. An ignored AuthError is also not established: the receipt never observed receipt of that message class. The existing silent-auth regression explicitly expects timeout and suppresses late acceptance ([test](/Users/SaintNick/Documents/Cortex/worktrees/backend-runtime-completion/tests/unit/client-runtime/client.test.ts:394)).

The exact external API limitation is that `setAuth` supplies a boolean callback for official auth state, while connection state alone cannot distinguish transport failure from credential denial. Convex's [onServerDisconnectError](/Users/SaintNick/Documents/Cortex/worktrees/backend-runtime-completion/node_modules/convex/src/browser/sync/client.ts:100) is explicitly experimental and supplies unstable strings only when a nonempty abnormal-close reason exists. Cortex's supported injected port has no terminal credential-rejection signal beyond setAuth. Reclassifying every silent timeout/disconnect as `UNAUTHENTICATED` would invent evidence and misclassify outages. Decoding unsigned `exp` before server confirmation would introduce local-clock assumptions; the official confirmed-token scheduler handles clock skew, so this is not an established compatibility-safe fix from the current evidence.

A concrete next **cause proof**, if the coordinator needs one on an already authorized read-only diagnostic, is to retain numeric close code, reason-present boolean, bounded reason UTF-8 byte count/SHA, and known static close/FatalError classes through the existing public Logger (or pinned experimental disconnect callback). Keep the same 4000ms auth deadline, original expected codes, zero protected/paid effects and cleanup. A reviewed exact server-auth denial classification could then justify a narrow client adapter; an unknown/transport close still remains timeout. This investigation does not authorize or perform that successor call and does not prescribe a speculative production change.

K9 failures and the actual K11 expired-token FAIL remain untouched. No timeout increase, assertion change, native-verifier acceptance or product completion claim follows from this report.
